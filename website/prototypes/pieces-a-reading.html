Understanding Claude

A working reference for developers who can code but have never built with agents, skills, or workflows. Every section stands on its own.

Verified against Anthropic's official documentation in August 2026. Anything that could not be confirmed is flagged and collected in the appendix.

01

How do all the pieces fit together?

Building with AI means moving work out of the chat window and into artifacts you can version, share, and re-run. The whole discipline is deciding which artifact a given piece of work belongs in.

As a full-stack developer you already know a version of this problem. You do not paste the same shell command into your terminal fifty times, you put it in a Makefile. You do not re-explain your API contract in every code review, you write it down. Working with AI tooling is the same instinct applied to instructions.

The common mistake

Choosing badly on this spectrum: repeating yourself when you should have written a skill, or writing a skill for something you will do once.

Every piece of guidance you give a model lives somewhere on a spectrum, and the building blocks below are just names for points on it.

Where it livesLifespanExample
A message you typeOne turnRename this variable
A conversationOne sessionFor this session, use British spellings
A file in your repoForever, for this projectBuild commands, code conventions
A packaged capabilityForever, across projectsYour team's PR review checklist

The three Claude surfaces

These are different products, not different models. Anthropic states that Cowork and Claude Code run on the same engine: both are Claude Code underneath.

SurfaceBest forHow it runs
Claude ChatA conversation you steer turn by turn You send a message, Claude replies, you react
Claude CoworkMulti-step work you delegate You describe an outcome, it plans and executes in a cloud sandbox
Claude CodeBuilding software Your terminal or IDE, with file system access
Worth knowing early

Skills you write for one surface do not automatically appear on the others. Custom skills do not sync across claude.ai, the API, and Claude Code.

How they nest

Each row below sits inside the one above it. This is one of the two panels on the page: a file listing is a machine surface, and it keeps a boundary so nobody reads it as prose.

02

What does any good prompt contain?

A good prompt is a brief for a competent stranger: role, objective, constraints, success criteria, format, and examples, with nothing left implied.

Anthropic's own analogy is the useful one: think of Claude as a brilliant but new employee who lacks context on your norms and workflows. The golden test they publish is to show your prompt to a colleague with minimal context and ask them to follow it. If they would be confused, Claude will be too.

IngredientWeakStrong
Role(omitted)You are a senior backend engineer reviewing a junior's PR.
ObjectiveLook at my codeFind bugs that would cause a 500 in production.
Context(omitted)Express API behind Cloudflare; req.user is set by middleware.
Constraints(omitted)Do not change the public API. Do not add dependencies.
Success criteriaMake it goodDone when every handler has an error path and tests pass.
Format(omitted)A Markdown table: file, line, severity, fix.
No longer current

Prefilling the final assistant turn returns a 400 on Claude 4.6 and later.

Manual chain of thought is now a fallback for when thinking is off. Current models use adaptive thinking and decide how much to reason on their own.

Two more pay for themselves whenever the task is fuzzy. Examples steer format more reliably than description does, three to five of them, relevant and structurally consistent. A not-doing list is the cheapest way to prevent a twenty-minute wrong turn.

prompt.txtexample
Role: You are a senior TypeScript reviewer.
Objective: Find correctness bugs in the diff below that tests would not catch.
Context: Node 22, Express 5. db.query returns null (not []) when no rows match.
Constraints: Do not propose refactors. Do not suggest new libraries.
Done when: Every issue names a file, a line, and a one-line fix.
Format: Markdown table, file | line | severity | fix.

03

How do I ask well in a conversation?

In Chat you are steering turn by turn, so front-load context and format, and let iteration do the rest. You see the result before anything is committed.

Nothing happens to your files or systems unless you use a tool or connector. The feedback loop is short and cheap, which is exactly what you should exploit.

The practical rule

In Chat you can be under-specified and recover. With an agent you pay for it.

ChatAgent
Unit of workOne replyOne completed task
Who decides the stepsYouThe agent plans and decomposes
Cost of a bad promptOne rewriteWasted execution, possibly file changes
CorrectionNext messageIdeally before it starts
Weak
my auth is broken can you help
No stack, no code, no ruled-out causes, no shape for the answer. Every reply to this starts by asking three questions.
Strong
Express 5 + jsonwebtoken. Login works, but every request to a protected route 401s. I have confirmed the token is present in the Authorization header and that JWT_SECRET matches between sign and verify.

Middleware:
[paste 15 lines]

Give me the 3 most likely causes, ranked, each with the one-line check that would confirm or rule it out.
Names the stack, rules out two dead ends, pastes the real code, caps the output at three items, and asks for falsifiable checks rather than a rewrite.
05

What is an agent, and when do I define one?

An agent is a model running in a loop with tools and a goal. It decides its own next step, which is exactly what makes it powerful and exactly what makes scope discipline mandatory.

An agent is not a special model. It is a model plus a goal, plus tools it can actually use, plus a loop in which it observes the result of each action and chooses the next.

The honest tradeoff

An agent trades predictability for reach. It will find paths you did not think of, and it will occasionally take one you did not want. Constraints are how you buy the predictability back.

A definition is only good if it answers five questions, and the first is the one people skip: what is this agent's single job? Agents with two jobs do both badly.

  1. What is this agent's single job?
  2. What may it touch, and what is off-limits? Encode it in the tool list, not in prose.
  3. What does it return to the caller?
  4. When should it stop or escalate?
  5. What must it never do?
.claude/agents/migration-reviewer.mdagent
---
name: migration-reviewer
description: Reviews database migration files for destructive or
  non-reversible operations. Use before any migration is merged.
tools: Read, Grep, Glob
model: sonnet
---

You review SQL migrations for safety only. You do not write or fix them.

For each migration file:
1. Flag DROP, TRUNCATE, and non-nullable ADD COLUMN without a default.
2. Confirm a documented rollback exists.

Return a table: file | risk (high/med/low) | reason | required change.
If no down-migration exists, mark the file high risk and stop.
One job, read-only tools so it cannot edit anything, a fixed output shape, and an explicit stop condition. All four are structural rather than polite requests.
07

When does packaged knowledge beat a prompt?

A skill is a folder of instructions Claude loads only when your request matches its description. It is how you stop re-explaining the same procedure in every conversation.

The mechanism that makes skills cheap is progressive disclosure: content loads in three stages, so until a skill is triggered it costs you a name and a sentence.

LevelWhen loadedCost
MetadataAlways, at startupAbout 100 tokens per skill
InstructionsWhen the skill is triggeredUnder about 5k tokens
ResourcesOnly when accessedNothing until read
Rule of thumb

If it is a fact about this project, it belongs in CLAUDE.md. If it is a procedure, it belongs in a skill.

the shape of one skilllisting
my-skill/one directory, one procedure
SKILL.mdrequired: frontmatter plus instructions
reference.mdoptional: detailed lookup material
examples.mdoptional
scripts/optional: the deterministic parts
validate.pyexits non-zero when it finds something
Portability trap

Outside Claude Code, only name, description, license, compatibility, metadata and allowed-tools are legal frontmatter. Anything else is a hard error.

Which one should I reach for?

Most beginner pain comes from picking the wrong container for the work. This table is the shortcut.

SituationReach forWhy
Explain this error to meChatYou want understanding, not artifacts
Reorganise 200 files and produce a summaryCoworkMulti-step, produces artifacts, worth walking away from
Fix this bug in my repoClaude CodeNeeds your real file system and dev tools
Every session should know our build commandsCLAUDE.mdA standing fact, not a procedure
I have explained this procedure three timesSkillPackage once, trigger by description
This step must be exactly right every timeScriptDeterminism beats instructions
40 files of output, I need 5 findingsSub-agentHigh noise-to-signal. Contain it
Audit all 300 files in this repoDynamic workflowMore agents than one conversation can coordinate
This must happen before every commitHookDeterministic enforcement, not instruction
My whole team needs this setupPluginVersioned, installable, namespaced
