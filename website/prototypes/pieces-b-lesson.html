Step 01 of 12

How do all the pieces fit together?

Building with AI means moving work into artifacts you can version, share and re-run. The discipline is deciding which artifact a piece of work belongs in.

You already know a version of this problem. You do not paste the same shell command into your terminal fifty times, you put it in a Makefile. You do not re-explain your API contract in every code review, you write it down.

Every piece of guidance you give a model lives somewhere on a spectrum. The building blocks in this phase are just names for points on it.

Where it livesLifespanExample
A message you typeOne turnRename this variable
A conversationOne sessionUse British spellings this session
A file in your repoForever, this projectBuild commands, conventions
A packaged capabilityForever, everywhereYour team's review checklist
The common mistake

Choosing badly on this spectrum: repeating yourself when you should have written a skill, or writing a skill for something you will do once.

Step 02 of 12

What does any good prompt contain?

A brief for a competent stranger: role, objective, constraints, success criteria, format and examples, with nothing left implied.

The golden test Anthropic publishes: show your prompt to a colleague with minimal context and ask them to follow it. If they would be confused, Claude will be too.

IngredientWeakStrong
Role(omitted)You are a senior backend engineer reviewing a PR.
ObjectiveLook at my codeFind bugs that would cause a 500 in production.
Constraints(omitted)Do not change the public API. No new dependencies.
Success criteriaMake it goodDone when every handler has an error path.
Format(omitted)A table: file, line, severity, fix.

Prefilling the final assistant turn returns a 400 on Claude 4.6 and later, and manual chain of thought is now a fallback for when thinking is off.

Step 03 of 12

How do I ask well in a conversation?

In Chat you steer turn by turn, so front-load context and format and let iteration do the rest.

Nothing happens to your files unless you use a tool or connector. The feedback loop is short and cheap, which is what you should exploit.

ChatAgent
Unit of workOne replyOne completed task
Who decides the stepsYouThe agent plans and decomposes
Cost of a bad promptOne rewriteWasted execution, possibly file changes
The practical rule

In Chat you can be under-specified and recover. With an agent you pay for it.

Step 04 of 12

How do I brief an agent that plans and executes?

Cowork commits to a plan before you see anything, so the prompt is a work order, not a question.

Three ingredients move from nice to load-bearing, because the agent decides when to stop and you are not there when it does.

  1. Done-when criteria. If you do not define done, it guesses.
  2. A not-doing list. Cheaply prevents scope creep that costs real execution time.
  3. Deliverable and destination. "A Markdown file in outputs" is checkable; "a summary" is not.
The tell

A good Cowork prompt reads like a ticket rather than a question.

Step 05 of 12

What is an agent, and when do I define one?

A model running in a loop with tools and a goal. It decides its own next step, which is what makes it powerful and what makes scope discipline mandatory.

An agent is not a special model. It is a model plus a goal, plus tools it can actually use, plus a loop in which it observes each result and chooses the next action.

The honest tradeoff

An agent trades predictability for reach. Constraints are how you buy the predictability back.

.claude/agents/migration-reviewer.mdagent
---
name: migration-reviewer
description: Reviews database migration files for destructive or
  non-reversible operations. Use before any migration is merged.
tools: Read, Grep, Glob
model: sonnet
---

You review SQL migrations for safety only. You do not write or fix them.

Return a table: file | risk | reason | required change.
If no down-migration exists, mark the file high risk and stop.
One job, read-only tools so it cannot edit anything, a fixed output shape, and an explicit stop condition. All four are structural rather than polite requests.
Step 06 of 12

When is delegation worth the cost?

A sub-agent works in its own fresh context and returns only a summary, which is the whole point and also the whole cost.

Delegate when the ratio of noise to signal is high. A sub-agent that reads forty files and returns five findings is a great trade. One that needs three clarifying rounds with you is a bad one: it cannot ask you anything mid-task.

The cost that surprises juniors

The sub-agent's context starts empty. It has not seen the file you were just discussing. If you do not put the facts in the delegation message, it will go and find them again, or guess.

Step 07 of 12

When does packaged knowledge beat a prompt?

A skill is a folder of instructions Claude loads only when your request matches its description.

The mechanism that makes skills cheap is progressive disclosure. Until a skill is triggered it costs you a name and a sentence.

LevelWhen loadedCost
MetadataAlways, at startupAbout 100 tokens per skill
InstructionsWhen triggeredUnder about 5k tokens
ResourcesOnly when accessedNothing until read
the shape of one skilllisting
my-skill/one directory, one procedure
SKILL.mdrequired: frontmatter plus instructions
reference.mdoptional: detailed lookup material
scripts/optional: the deterministic parts
validate.pyexits non-zero when it finds something
Rule of thumb

If it is a fact about this project, it belongs in CLAUDE.md. If it is a procedure, it belongs in a skill.

Step 08 of 12

When do I want code instead of instructions?

A script is the part of a skill you do not want the model improvising. It costs you only its output, not its source.

One-off promptReusable script
DeterminismVaries run to runIdentical every time
Context costThe whole thing, every timeOnly its output
Fails byBeing subtly wrongBeing loudly wrong
The rule

Write a script when being wrong is worse than being slow. Anything with a right answer is script territory; anything requiring taste stays in instructions.

Step 09 of 12

How do I orchestrate work at scale?

A dynamic workflow is a JavaScript script, written by Claude, that orchestrates sub-agents in the background while your session stays responsive.

The key inversion: with skills and sub-agents Claude holds the plan and decides step by step. With a workflow the script holds the plan, which is what lets it coordinate far more agents than one conversation can track.

Permission gotcha worth memorising

Sub-agents spawned by a workflow always run in acceptEdits mode regardless of your session's permission mode. File edits are auto-approved. Do not point a workflow at code you are not prepared to have modified.
